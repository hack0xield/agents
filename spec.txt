# AI Trading Assistant Infrastructure Specification

**Version:** 0.1
**Product:** B2C AI Trading Assistant for Prop Traders
**Primary channel:** Telegram
**Initial trading platform:** MetaTrader 5
**Initial customer:** Founder / User #1
**Target architecture:** 1,000+ paying users
**Implementation assumption:** one Architect-level engineer using AI coding tools

---

# 1. Product Definition

The product is a persistent AI trading assistant for retail and prop traders.

The assistant combines:

1. a general-purpose frontier LLM;
2. a proprietary database of precomputed backtests;
3. real-time read-only access to the user's MT5 account;
4. deterministic real-time pattern detection;
5. market-calendar and trading-event monitoring;
6. trading discipline monitoring;
7. persistent user-specific memory;
8. proactive communication through Telegram.

The assistant **does not execute trades**.

The assistant observes, analyses, retrieves historical evidence, identifies relevant situations and communicates with the trader.

Its core purpose is not:

> "Tell me whether EURUSD will go up."

Its core purpose is:

> "Tell me whether something is happening now that resembles a scenario we have previously tested, what the historical evidence says about it, whether there are important contextual events, and whether my current behaviour violates my own trading rules."

---

# 2. Fundamental Architectural Principle

The LLM must **not continuously analyse market data**.

It must not receive every tick, every candle update or every account update.

Instead:

```text
MARKET / MT5 / CALENDAR
          ↓
DETERMINISTIC EVENT ENGINE
          ↓
     Is anything
     interesting?
      ↓       ↓
     NO      YES
     ↓        ↓
  nothing   structured event
              ↓
        AGENT ORCHESTRATOR
              ↓
             LLM
              ↓
          Telegram
```

The infrastructure watches the market.

The LLM interprets and communicates significant events.

This separation is critical for:

* token cost;
* latency;
* scalability;
* reproducibility;
* auditability;
* false-positive control;
* future model independence.


# 3.4 MT5 Connection

The bot must **not ask the user to send the MT5 password inside Telegram chat**.

Instead it sends a secure link:

> Connect MT5 Account

The user opens an authenticated HTTPS page and enters:

```text
MT5 login
MT5 investor password
Broker / Prop Firm
MT5 server
Account nickname
```

Example:

```text
Login: 10534821
Server: FTMO-Demo2
Password: ***********
Nickname: FTMO 100K Challenge
```

Only an **Investor Password** is accepted.

The master trading password must never be accepted.

MT5 explicitly supports investor mode as read-only access: trading is disabled when connected using the investor password. MT5 documentation also states that OTP is not required when connecting in read-only investor mode.

Successful connection creates:

```text
TradingAccount
MT5Connection
RiskProfile
AccountState
```

Assistant sends:

> FTMO 100K Challenge connected.
>
> Balance: $100,000
> Equity: $100,000
> Open positions: 0
>
> Monitoring is active.

# 5. Technology Strategy

## 5.1 Do Not Start With Microservices

For one engineer, the initial implementation should be a **modular monolith plus asynchronous workers**.

Suggested stack:

### Core backend

Python + FastAPI.

Reasons:

* strong data-processing ecosystem;
* MT5 Python integration;
* good Anthropic SDK support;
* easy background jobs;
* good statistical tooling.

### Frontend

Next.js.

### Primary database

PostgreSQL.

### Vector retrieval

PostgreSQL + vector extension initially.

Do not introduce a dedicated vector database until scale demonstrates a real requirement.

### Cache / queue

Redis.

### Object storage

S3-compatible object storage.

Used for:

* PDF/HTML backtest reports;
* raw backtest datasets;
* charts;
* exports;
* audit artifacts.

### Background jobs

Celery / Dramatiq / equivalent lightweight queue.

### Secrets

Cloud Secrets Manager / Vault/KMS.

### Deployment

Linux containers for normal services.

Dedicated Windows workers for MT5 terminal connectivity.

# 6. OpenClaw Decision

OpenClaw is useful for the **User #1 prototype**.

It already supports:

* Telegram;
* tools;
* skills;
* plugins;
* persistent memory;
* model providers.

Its Telegram channel is production-supported, and its skill system can inject skill instructions into the agent context.

However, OpenClaw's own architecture documentation describes it primarily as a personal assistant for a **single trusted operator**. Its security documentation explicitly states that one shared Gateway is not intended to provide hostile multi-tenant isolation. Separate tenant instances are recommended, and its fleet-based multi-tenant hosting remains experimental.

Therefore:

## Recommendation

### User #1 / Prototype

OpenClaw may be used as:

```text
Telegram
   ↓
OpenClaw
   ↓
Claude
   ↓
our MCP tools
```

This gives extremely fast product validation.

### Production

OpenClaw must **not be a mandatory architectural dependency**.

Production should evolve toward:

```text
Telegram
    ↓
Our Agent Orchestrator
    ↓
Claude API
    ↓
Our tools / MCP
```

OpenClaw can remain:

* a development sandbox;
* a reference implementation;
* an internal founder assistant;
* potentially an isolated per-user runtime for special accounts.

But the SaaS identity, subscriptions, permissions, backtests, alerts and trading telemetry must belong to our Product Core.

# 8. LLM Strategy

The LLM provider must be abstracted behind:

```text
LLMProvider
```

Example:

```python
generate_response()
call_tool()
summarize_session()
classify_event()
```

This allows future replacement or combination of:

* Anthropic;
* OpenAI;
* other providers.

For the current implementation, Claude is a sensible default.

As of August 2026, Anthropic positions Sonnet 5 as the speed/intelligence balance, Haiku 4.5 as its lowest-cost current tier, with Opus 5 and Fable 5 available for more demanding reasoning workloads. Current API pricing listed by Anthropic is $2/$10 per million input/output tokens for Sonnet 5 and $1/$5 for Haiku 4.5.

Recommended routing:

```text
NO LLM
    │
    ├── deterministic notifications
    │
Haiku
    │
    ├── classification
    ├── summarisation
    └── low-value transformations
    │
Sonnet
    │
    ├── normal conversation
    ├── trading explanations
    ├── proactive commentary
    └── backtest interpretation
    │
Opus/Fable
    │
    └── optional deep analysis
```

Sonnet should therefore be the normal "brain".

The expensive model must be an **exception**, not the default.

# 9. Agent System Behaviour

The permanent system instructions must establish the following behavioural principles.

## 9.1 Evidence hierarchy

The assistant distinguishes between:

### Level A

Verified proprietary backtest evidence.

### Level B

Current deterministic account or market data.

### Level C

External factual market information.

### Level D

General LLM reasoning.

The assistant must never present D as A.

---

# 9.2 No invented backtests

If the user asks:

> What does the backtest say about this setup?

The assistant MUST call:

```text
backtests.search()
```

If no matching backtest exists:

> We don't currently have a validated backtest for this exact scenario.

It must never generate plausible statistics.

---

# 9.3 Wording of statistical evidence

Avoid:

> This pattern has been statistically proven to work.

Prefer:

> Under the tested historical conditions, this pattern demonstrated positive historical expectancy.

The distinction matters because historical evidence is conditional on:

* sample period;
* market regime;
* instrument;
* execution assumptions;
* sample size;
* spread/slippage;
* parameter selection;
* out-of-sample behaviour.

---

# 9.4 Behavioural observations

Assistant must not tell the trader:

> You are emotional.

Instead:

> Your last three trades show a behaviour consistent with revenge trading: position size increased after two consecutive losses and the third entry occurred four minutes after the previous stop-out.

Observation first.

Interpretation second.

Anthropic's Agent SDK supports MCP-connected external tools and data sources, including in-process custom MCP tools.

However:

**MCP is not the real-time event transport.**

It should be used when the agent asks:

> Give me this account's positions.

Not for:

```text

tick
tick
tick
tick

```

This is one of the core proprietary assets of the business.

The backtest system must produce two outputs.

## Human-readable output

Report containing:

* hypothesis;
* conditions;
* instruments;
* timeframe;
* tested period;
* sample size;
* entry logic;
* exit logic;
* risk rules;
* results;
* distributions;
* limitations;
* charts.

## Machine-readable output

Structured object.

Example:

```json
{
  "pattern_id": "XAU_H4_MZ_REVERSAL",
  "version": 4,
  "instrument": "XAUUSD",
  "timeframe": "H4",
  "tested_from": "2015-01-01",
  "tested_to": "2026-01-01",
  "sample_size": 438,
  "win_rate": 0.57,
  "expectancy_r": 0.21,
  "profit_factor": 1.34,
  "conditions": {},
  "invalidations": {},
  "detector_version": "4.2"
}
```

# 13. Backtest Versioning

Backtests must be immutable.

Never silently overwrite:

```text
Pattern A v3
```

with new statistics.

Instead create:

```text
Pattern A v4
```

Each live alert stores:

```text
pattern_version
detector_version
backtest_run_id
```

Therefore six months later we can reconstruct exactly:

> Why did the system send this alert?

---

# 14. Live Pattern Detection

Every backtested strategy intended for real-time monitoring must provide a machine-readable detector.

Architecture:

```text
Backtest
    ↓
Pattern Definition
    ↓
Live Detector
    ↓
market data
    ↓
PatternEvent
```

Example:

```text
PATTERN_DETECTED

pattern = XAU_H4_MZ_REVERSAL
version = 4
instrument = XAUUSD
time = 14:00 UTC

historical_sample = 438
historical_expectancy = +0.21R
historical_win_rate = 57%

current_conditions = [...]
```

Only then is the LLM called.

---

# 15. Compute Once, Notify Many

This becomes crucial at 1,000 users.

Suppose 600 users watch XAUUSD.

Do **not** run the XAUUSD pattern detector 600 times.

Run:

```text
XAUUSD detector
       ↓
PatternEvent
       ↓
Subscribers matching event
       ↓
User-specific filtering
       ↓
notifications
```

This means:

**market intelligence is computed per market, not per user.**

Personalisation happens afterwards.

# 18. Multi-user MT5 Architecture

At scale, the system should operate a fleet of isolated MT5 connector workers.

Conceptually:

```text
             Account Registry
                    ↓
            Connector Scheduler
                    ↓
    ┌───────────────┼───────────────┐
    ▼               ▼               ▼
Worker A         Worker B         Worker C
Windows          Windows          Windows
MT5 instances    MT5 instances    MT5 instances
```

Each account has an assigned connector.

Connector health:

```text
CONNECTED
DISCONNECTED
AUTH_FAILED
STALE
RECONNECTING
```

The actual number of terminal instances sustainable per worker must be established through load testing rather than hard-coded as an architectural assumption.

---

# 19. Future Alternative: Local Bridge

Server-hosted MT5 terminals introduce infrastructure cost because every connected account requires persistent connectivity.

Therefore a future alternative should be supported:

```text
User PC
  ↓
lightweight EA / local connector
  ↓ encrypted websocket
Cloud
```

Advantages:

* no investor password stored by us;
* reduced MT5 cloud infrastructure;
* easier account scaling.

Disadvantage:

* user must install software;
* monitoring stops when terminal/device is offline.

For the initial B2C experience, server-side Investor Password connectivity is preferable because onboarding is much simpler.

# 21. Skill Architecture

A skill must **not merely be another giant prompt**.

Each skill should contain:

```text
Skill
├── manifest
├── deterministic logic
├── trigger definitions
├── required data
├── tools
├── LLM instructions
├── notification policy
└── tests
```

Example:

```yaml
id: options_expiry
version: 2

triggers:
  - scheduled
  - relevant_position_open

required_data:
  - expiry_calendar
  - open_positions

severity:
  default: informational

llm:
  required: false
```

This design is similar conceptually to OpenClaw's separation between tools, skills and plugins, but adapted to a multi-tenant SaaS rather than loading everything into a personal agent's prompt. OpenClaw itself describes skills as instructions teaching an agent how and when to use tools.

# 28. Discipline Engine

This should be one of the strongest differentiators of the product.

It analyses account behaviour without an LLM.

Examples of deterministic signals:

### Risk increase after loss

```text
normal risk = 0.5%
loss
next trade risk = 1.2%

→ RISK_ESCALATION
```

### Revenge-like re-entry

```text
trade stopped
3 minutes later
same instrument
same direction
larger size

→ POSSIBLE_REVENGE_TRADE
```

### Overtrading

```text
historical median = 3 trades/day

today = 11

→ OVERTRADING_ALERT
```

### Stop widening

```text
initial SL = -0.7R
modified SL = -1.4R

→ STOP_WIDENED
```

### Loss chasing

```text
3 losses
position size:
0.5%
0.5%
1%
2%

→ LOSS_CHASING_SEQUENCE
```

---

# 29. LLM Role in Discipline Monitoring

The detector identifies the event.

The LLM explains it.

Input:

```text
POSSIBLE_REVENGE_TRADE

last_trade:
loss -0.48%

time_since_close:
4m 12s

new_trade:
same symbol
same direction

risk:
1.02%

user normal risk:
0.5%
```

Possible assistant response:

> Quick check before you continue.
>
> You were stopped on XAUUSD four minutes ago and have just re-entered in the same direction at roughly twice your normal risk.
>
> I can't know whether you're trading emotionally, but this matches the loss-chasing behaviour you asked me to flag.
>
> Was this second entry part of the original plan?

This is vastly better than:

> You are revenge trading.

Do not ask Sonnet/Opus to decide:

> Is today December 31?

Code can do that.

Do not ask an expensive model to convert:

```text
severity=HIGH
```

into a fixed notification if a template is sufficient.

---

# 46. Rough LLM Cost Example

Illustratively:

```text
1,000 users
10 LLM-generated proactive messages/day
30 days

= 300,000 generations/month
```

If an average Sonnet generation used approximately:

```text
1,000 billable input tokens
250 output tokens
```

then using Anthropic's current $2 input / $10 output per million Sonnet 5 tokens would imply approximately:

```text
Input:
300M × $2/M = $600

Output:
75M × $10/M = $750

Total:
≈ $1,350/month
```

excluding interactive chat and other infrastructure. Current model pricing is documented by Anthropic.

If the architecture accidentally sends 5-10x more context with every request, that number expands correspondingly.

Hence **context engineering matters almost as much as model choice**.

# 47. Security Requirements

This product holds sensitive financial-account information.

Mandatory requirements:

## Credentials

MT5 Investor Password:

* encrypted at rest;
* encrypted in transit;
* stored only in Secrets Manager;
* never placed in PostgreSQL plaintext;
* never sent to Claude;
* never logged;
* never returned by APIs;
* never visible to support personnel by default.

The LLM receives only:

```text
account_id
```

not credentials.

# 48. Tenant Isolation

Every persistent object must contain:

```text
tenant_id / user_id
```

and authorization must be enforced server-side.

Critical tests must attempt:

```text
User A → retrieve User B memory
User A → retrieve User B positions
User A → retrieve User B backtests marked private
```

Expected result:

```text
DENIED
```

No cross-user leakage is acceptable.

# 49. Tool Security

LLM tools must use allowlists.

Assistant cannot arbitrarily:

* run shell commands;
* query unrestricted SQL;
* access filesystem;
* browse user secrets;
* call arbitrary URLs.

This is another reason not to expose a general-purpose autonomous OpenClaw installation directly to 1,000 unrelated customers.

# 63. Important Product Constraint

The assistant must not become a **signal-selling bot with better prose**.

Its identity should consistently remain:

That means it should often say:

> Nothing worth doing right now.

Or:

> We do not have enough evidence for this scenario.

Or:

> This setup does not match any pattern currently present in our validated database.

Those responses are features, not failures.

# 66. Definition of Success for User #1

The first product milestone is achieved when the following scenario works end-to-end:

### Morning

Assistant spontaneously sends:

> Good morning.
>
> CPI is at 13:30 London time.
>
> XAUUSD has no confirmed backtested setup currently.
>
> Your FTMO challenge is connected and has no open positions.

### During trading

A proprietary pattern appears.

Assistant sends:

> XAUUSD has just confirmed Pattern MZ-04 on H4.
>
> Historical dataset: 438 occurrences.
>
> Historical expectancy under the tested conditions: +0.21R.
>
> Want the full backtest?

### User

> Yes.

Assistant retrieves the **existing** backtest report.

### Later

User loses two trades and immediately doubles risk.

Assistant sends:

> Quick check.
>
> Your last two trades were losses and the new position is approximately twice your normal risk.
>
> This matches the loss-escalation behaviour you've asked me to flag.
>
> Is the increased risk part of the original trading plan?

### Evening

Assistant sends:

> Today:
>
> 4 trades
> -1.3R
> 1 discipline alert
> 1 valid pattern traded
>
> Your largest deviation was increasing risk after the second loss.
>
> Want to review the sequence?

If this experience is genuinely useful to User #1, the system has the nucleus of the product.

# 67. Final Architectural Position

The product should be thought of as five layers:

```text
┌─────────────────────────────────────┐
│ 5. EXPERIENCE                       │
│ Telegram / Web                      │
├─────────────────────────────────────┤
│ 4. INTELLIGENCE                     │
│ Claude + Agent + Memory             │
├─────────────────────────────────────┤
│ 3. DECISION SUPPORT                 │
│ Patterns / Risk / Skills / Events   │
├─────────────────────────────────────┤
│ 2. PROPRIETARY KNOWLEDGE            │
│ Backtests / Trading methodology     │
├─────────────────────────────────────┤
│ 1. DATA                             │
│ MT5 / Market data / Calendar        │
└─────────────────────────────────────┘
```

The moat should primarily develop in Layers **2 and 3**.

The LLM itself will continuously become cheaper and more commoditised.

Telegram is replaceable.

Stripe is replaceable.

Even the agent framework is replaceable.

What becomes difficult for a competitor to reproduce is:

```text
years of structured backtests
+
live pattern definitions
+
discipline models
+
trading-event logic
+
user behavioural history
+
data connecting real trader behaviour to tested scenarios
```

That is therefore where the architecture should concentrate proprietary value.

The AI is the interface to that intelligence, not the intelligence itself.
